# Features

This list is generated from the Cucumber scenarios in [`features/`](features).
Do not edit this file. After a change to a `.feature` file, run
`mise run features`.

## Import

Source: [`features/import`](features/import).

### Applying an import

muzik puts the planned songs into the library folder, writes their tags, and adds them to the beets library.

- The best match gives the song clean tags, a cover, and its source
- A singleton goes to the singleton path and gets no album
- A move removes the incoming song after the library write
- A beets replace rule changes the destination

### Cancelling an import

The user can cancel an import at any time. A cancelled import leaves the incoming songs, the library folder, and the beets library as they were.

- Cancelling before the import starts changes nothing
- Cancelling after the first file is moved puts the files back

### Duplicate albums

When an album is already in the library, the user decides to keep both, skip the new album, or replace the old one.

- A dry run writes nothing, and a duplicate needs a decision
- An album whose files are already in the library is skipped
- Replace removes the duplicate album the user selected
- Replace keeps an album from a release the user did not select
- Replace can reuse the destination of the old album
- A failed replace restores the old album and its file

### Incremental import

With incremental import on, muzik remembers which folders it imported and does not import them again.

- An imported folder is added to the history
- A skipped folder is added to the history unless skip later is on
- A dry run does not write the history
- A folder from the history is skipped, and a real run saves the history

### Filling MusicBrainz ids

muzik finds the MusicBrainz release of a library album that has no MusicBrainz id. It writes only the ids and keeps all other tags and fields.

- A strong match writes only MusicBrainz ids to the files and the library

### Import plan

Before muzik imports anything, it groups the files into albums and looks for matching releases on MusicBrainz. The plan shows what the import will do.

- Songs in an album folder become one album matched to a release
- An album is planned as it is when MusicBrainz fails
- With autotag off, muzik plans the import without MusicBrainz
- Cancelling during the MusicBrainz search stops the plan

### Library sync

muzik refreshes library entries from MusicBrainz. It updates the beets library and the tags in the audio files.

- Sync updates an album and the tags of its file
- Sync updates a singleton by its recording

### Importing tagged albums

muzik imports albums the way beets does: the same paths, the same library fields, and the MusicBrainz ids of the matched release.

- A tagged FLAC file imported as it is gets the beets path and fields
- An album matched to a recorded MusicBrainz release is imported

## Library

Source: [`features/library`](features/library).

### Cover files

muzik saves album art next to the tracks, finds cover files in album folders, and reads the front cover that is in the track tags.

- Image data gets the file extension of its format
- A cover file is written once and never replaced
- A folder cover has the configured name or a usual name
- The front cover comes from the first track that has one

### Searching the library

muzik understands beets queries. A query finds the same items and albums, in the same order, as beets finds.

- A query finds the items that beets finds
- A query finds the albums that match album fields
- Items without a sort are in order of the artist sort name
- Albums without a sort are in order of the album artist sort name

### Reading the library

muzik reads the items and albums of a beets library, with their fixed fields and their flexible fields.

- Items keep their fixed and flexible fields
- Albums keep their fields and their items

### Writing to the library

muzik adds, changes and removes items and albums in a beets library. A group of writes is all or nothing, and muzik keeps a backup of the library.

- The first write makes a new library
- Fixed and flexible fields are written in one group
- A failed group of writes changes nothing
- Pruning stops before it removes too many items
- Pruning removes the items whose files are missing

## Sync

Source: [`features/sync`](features/sync).

### Removing old files from the device

With delete on, a sync removes the files on the device that are not in the selection. muzik keeps them when it cannot read all the selected tracks.

- A track that muzik cannot read stops the delete
- Old files are set for removal when muzik can read all tracks
- The sync removes old files and copies the new tracks
- An old file that is already gone does not stop the sync
- The sync changes nothing when the device is unplugged

### Writing files to the device

muzik writes each file to the device in full or not at all, and it tells the user about files whose sync record it could not save.

- A copied file is complete and keeps the source permissions
- A failed copy keeps the earlier device file
- Transfers whose record muzik cannot save are counted

### Converted files on the device

muzik records the encoding of each file that it converts. A converted file is current only when the record matches the encoding that the target needs.

- A converted file with no record is converted again
- A converted file with a matching record is current
- A new bitrate converts the file again
- A plain copy removes the recorded encoding

### Device formats

Each sync preset decides if muzik copies a track as it is or converts it to a format that the device plays.

- The Echo Mini preset keeps audio that it plays and converts the rest
- The Opus preset converts lossless audio and keeps common lossy audio
- The MP3 preset converts all audio except MP3

### Old files on the device

muzik treats media files that are not in the sync plan as old. Hidden files from macOS and from stopped syncs are old too. Other files stay.

- Unplanned media and hidden leftovers are old

### Sync planning

Before muzik writes to the device, it plans where each library file goes, which files are already current, and which files it must skip.

- Destinations keep the library folders with names that the device accepts
- Files that are already on the device are not copied again
- Only one track goes to each file name on the device

### Selecting library tracks to sync

A library query selects the tracks to sync. With covers on, the album cover files go to the device with the tracks.

- With covers on, muzik selects the tracks and the album cover
- With covers off, muzik selects no covers

### Sync targets

A sync target names a device folder and the format settings for it. muzik keeps the targets in the config file with the other settings.

- A saved target loads with the same settings
- An unknown target name gives the names of the known targets
- A bitrate that is too high is refused

## Watchlist

Source: [`features/watchlist`](features/watchlist).

### Watchlist item actions

The user runs an action on one watchlist item, for example run, retry, or download again. A question pauses the item at the stage that asked it. A failure is saved on the stage that failed.

- Each question pauses the item at its own stage
- An action that needs a choice parks the item
- A failed action saves the stage of the action
- An action checks the identity of the saved item
- A failure marks the stage that failed
- Downloading again keeps later stages stale after a check of the cache

### Watchlist cards

Each watchlist item shows as a card with a summary, a main action, the actions that the user can take, and a cached thumbnail. Showing the cards does not change the saved watchlist.

- A new video shows the run action and its cached thumbnail
- A removed or private video is not shown as failed
- A video that failed for another reason can be retried

### Local check of the watchlist

When the watchlist page opens, muzik shows the saved state at once and then checks the local files in the background. The result of the check is saved and shown only while no job runs and no newer edit or check started.

- A local check shows the saved state first and then the checked state
- A local check does nothing while a job runs
- A local check is outdated when another check starts while it reads the settings
- A local check that is outdated changes nothing
- A revision conflict loads the outside edit before the check saves
- Repeated revision conflicts report an error and keep the outside edit

### Watchlist state from local files

muzik checks the saved watchlist against the downloaded files, the split folders, the cache of earlier versions, and the music library. A finished stage is marked complete. A video that is not finished leaves the processed list.

- Finished stages are filled in and a waiting stage keeps its question
- An import that the cache left open fails once
- A second check changes no rows
- A kept source file with an empty split folder stays processed
- A video that is already in the music library is complete
- Old cache entries for a YouTube video and a Spotify track are read

### Old watchlist file

Earlier versions of muzik kept the watchlist in a JSON file. muzik moves that file into the database once, keeps a backup, and keeps the saved state of each item. muzik does not move a file that it cannot read.

- An old watchlist file moves into the database with its item state
- Saving the moved watchlist again changes nothing
- An old watchlist file that muzik cannot read stays in place

### Watchlist refresh

A refresh reads each watched source, adds new videos, and processes each video that is not finished. A sync only reads the sources and lists the videos that wait for processing. Both keep the saved state of each item.

- A refresh keeps earlier state and processes each video once
- A video that waits for an answer does not block the refresh
- A refresh reads every source before it processes items
- A refresh of one source reads and processes only that source
- A refresh of a source that is not watched fails
- A cancelled refresh keeps the videos saved before the stop
- A dry run changes nothing and processes no audio
- A sync lists pending videos and keeps running stages
- A private video is not queued and shows as unavailable

### Saving the watchlist safely

The desktop app, the command line, and the job runner can change the watchlist at the same time. A checked write saves only when nobody changed the watchlist after it was read, so no change is lost.

- A checked write keeps a source edit made at the same time
- A checked write keeps a stage change made at the same time
- A checked write of an unchanged watchlist keeps the revision
- A checked write that fails changes nothing
- Parallel updates keep every change

### Watchlist sources

The user adds YouTube playlists, Spotify playlists, albums, liked songs, and the Bandcamp collection to the watchlist. The user can rename and remove a source. A change to a source keeps the state of its items.

- A link from a supported service is accepted
- A link from another host is rejected
- A YouTube video link adds the playlist of the video
- The same playlist cannot be added twice
- Spotify sources get a Spotify ID
- Liked songs get their own title
- Renaming a source keeps the state of its items
- Removing a source keeps the other sources
- The Bandcamp collection is added once

## Workflow

Source: [`features/workflow`](features/workflow).

### Chapter split

The workflow splits an audio file with chapters into album tracks. Then it organizes the split folder.

- A local album with chapters is split and then organized
- The YouTube description gives the chapters
- Rejected chapters make the source a single
- Edited chapters reach the split
- With no split, chaptered audio stays one import target
- A forced split rejects a dot-only album name and keeps other files
- A better-quality album replaces the source without a chapter split

### Workflow events

The workflow reports its progress as events. The receiver of the events can cancel the run.

- The event receiver cancels the run before the split
- Events report the track progress and the completion

### Workflow inputs

The workflow accepts a local path, a YouTube video, a YouTube playlist, a Spotify export, or a search text. It finds the kind of input first.

- A local Spotify CSV file is a Spotify export
- A watch URL with a list is a playlist, not a video
- A short link is a YouTube video
- Audio discovery follows links and finds each file once
- Audio discovery stops at a link loop

### Playlists

The workflow runs each item of a YouTube playlist or a Spotify export in order. A failed item does not stop later items. A new run continues from the items that are not complete.

- A YouTube playlist keeps its order and continues after a failure
- A YouTube playlist run continues from the failed item
- The main workflow sends a playlist URL to the playlist run
- A Spotify export with a repeated track runs each position
- A complete Spotify export run gets no audio again
- A Spotify CSV export keeps quoted names
- A Spotify CSV export with a repeated position is rejected
- A Spotify JSON export with an invalid position is rejected

### Audio sources

The workflow gets audio from YouTube or Soulseek. It can fall back from Soulseek to YouTube when Soulseek has no result.

- A video that is already downloaded is not downloaded again
- A dry run plans the work but changes no files
- Soulseek is the audio source for a search
- A cancelled workflow does not import
- A video comes from Soulseek when Soulseek has a result
- YouTube is the fallback when Soulseek has no result
- Cancellation during the Soulseek search stops the fallback
